# 프로젝트 상세 콘텐츠

프로젝트 이름, 대표 이미지, 저장소와 공개 정책은 [projects.ts](../src/data/projects.ts)에서 관리합니다. 상세 콘텐츠는 `projects/<slug>/<원본 슬라이드 번호>-<판본>.md`에서 관리합니다. 한 프로젝트에 클라이언트와 서버, 원작과 리메이크 등 여러 문서를 둘 수 있습니다.

[Pong 게임](projects/pong/18-client.md)과 [Pong 서버](projects/pong/44-server.md)는 같은 `pong` 프로젝트의 서로 다른 구현입니다. [발전소 이야기](projects/powerstationstory/37-powerstationstory.md)는 원본 37쪽에 대응합니다. 숫자는 원본 PPTX의 슬라이드 순서입니다.

## Markdown 형식

문서의 첫 줄은 판본 제목(`#`)입니다. 다음 JSON 코드 블록에 원본 정보를 기록하고, 그 아래에 본문을 작성합니다.

| JSON 필드 | 형식 | 내용 |
|---|---|---|
| `period` | 문자열, 필수 | 원본에 적힌 기간. 연도만 있거나 종료 시점이 비어 있는 경우도 보존 |
| `stack` | 문자열 배열, 필수 | 해당 판본의 기술과 개발 환경 |
| `images` | 객체 배열, 필수 | PPTX 내부 `ppt/media/`의 파일명(`file`)과 원본 픽셀 크기(`width`, `height`). 슬라이드에 등장하는 순서로 기록 |
| `team` | 문자열 | 원본에 기재된 팀 규모·직무별 인원 |
| `highlightedTeamRole` | 문자열 | 기존 PDF의 팀 구성에서 강조한 직무 |
| `role` | 문자열 | 공개 근거로 확인한 담당 역할 |
| `pending` | 문자열 배열 | 검증 대기 항목명. 검토 중인 수치·수상 내역·개인 정보는 로컬 원본에서 관리 |

`## 개발 목적`에는 판본의 목적을, `## PPTX 기록`에는 원본에 적힌 기능을 목록으로 작성합니다. 공개 코드나 발표 자료로 대조한 경우 `## 공개 자료로 확인한 내용`에 확인한 구현·결과와 해당 커밋의 파일 링크 또는 DOI를 적습니다. `## 관련 링크`에는 확인한 시연 영상과 웹 게임 링크를 둘 수 있습니다.

그림 참조는 원본에서 해당 그림을 찾기 위한 값입니다. 사용 범위를 확인한 그림을 배치할 때에는 기록된 가로·세로 비율을 유지합니다.

## 공개 정책 및 검증

`publication.web`과 `publication.pdf`는 각각 `true`(공개), `false`(제외), `null`(미결정)로 관리합니다. Markdown 등록만으로 웹이나 PDF 수록 대상이 되지 않습니다. 웹은 기존과 같이 대표 이미지와 공개 저장소가 있는 공개 대상만 표시합니다.

```bash
npm run validate:projects
```

검증기는 디렉터리의 slug로 프로젝트를 연결하고 원본 7–45쪽의 누락, 번호·판본 중복, 메타데이터와 본문 형식을 검사합니다. `loadProjectContent()`는 검증된 문서를 원본 번호 순으로 반환합니다. 각 문서의 `project`에서 채널별 공개 정책을 확인할 수 있습니다. `npm run build`에서도 같은 검증을 실행합니다.
